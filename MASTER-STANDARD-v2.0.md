## 2. Five-layer architecture
1. Entry System — recognise intent from direct, menu, search, campaign, partner and quiz entry.
2. Knowledge Graph — identify relevant opportunities, constraints and enabling competencies.
3. Landing Generation — reveal opportunities through VRL and cultural presentation.
4. Demand Intelligence — measure aggregate demand and route performance; no contact details in telemetry.
5. Execution Intelligence — CRM and future TwinMind orchestration, delivery and measurement. Do not depict as operational until tested.
Feedback: completed work and measured results enrich the graph.

## 3. Domain contract
Eight axes: subject, state, intent, origin, destination, industry, scale, task (derived, not asked). Separate geographic direction (inbound/domestic/outbound/regional) from transition (development/transformation/integration/protection). Seven subject models: customer, strategic client, partner, specialist, representative, referrer, investor. Each has a distinct relationship and next step.
Current and Desired are elicited; Potential is established through paid architectural diagnosis. Public potential maps are conditional illustrations, not a promised individual outcome.
Graph node types: intent, state, opportunity, barrier, transition, competence, evidence, value, resource, offer. Edge types: opens, limits, enables, requires, proves, amplifies.
Routes: enter, expand, grow, transform, protect, integrate, invest, network, connect, represent, semantic. Preserve existing URLs or redirects. Ask only missing relevant questions, default optional question budget four. No false inference from geography.
Use stable identifiers and versioned schemas, independent of language. Validate references, enums, links and language completeness at build time.

## 4. Commercial loop
Entry → recognition → qualification → diagnosis → proposal → agreement → design → implementation → measurement → case → graph improvement.
Free orientation; paid diagnosis; individually agreed design, execution and support. Brand ladder: NAME, IDENTITY, BRAND ARCHITECTURE, BRAND LAUNCH, GLOBAL BRAND. Independent offerings: Semantic Architecture, Business Ontology, Enterprise Knowledge Graph, AI-Ready Architecture, Central Asia Market Entry. Scope and price depend on target market, volume, scale and localisation. No public prices without approval; no private price matrices in a public repo or browser build.
Context ID describes the validated intent context; a separate opaque enquiry ID identifies one request across channels. Do not include personal data in either ID or URL; attach contact information only to the deliberate enquiry. Server-side validation, idempotency, rate limits and explicit delivery status. A mailto link is a handoff, not delivered mail.
Public contact: rootfrontier.office@gmail.com. Corporate affiliation links to rootfrontier.systems; corporate phone is not published on YISHU. Additional channels enabled only after configuration and consent.
CRM/payment integration is incomplete until end-to-end evidence exists; do not invent payment routes or legal operator.

## 6. Cultural and experience engine
Preserve RU, KY, KK, UZ, ZH, EN (existing language contours). Translate meaning, examples, tone and argument order, not just words; review with fluent speakers. Language preference is explicit and persistent, browser/region only a suggestion. Never force redirects. Culturally adapted blocks must actually be rendered. No advertised untranslated route; provide explicit fallback if missing. China readiness: local assets, no mandatory blocked CDN, real access test from mainland before claim.
PES: ATTRACTION, VRL, ARCHITECTURAL REVEAL, RBDA, CEA, LIVE DEMONSTRATION, COLLABORATION, VISUAL FIDELITY. Perception architecture → visual scenario → WOW hero → interactive prototype → product website → mobile/desktop QA → corrections → publication → real browser check. Meaningful diagrams, accessible controls, keyboard navigation, no horizontal overflow, reduced motion, clear light/dark contrast. Remove redundant meaning. Preserve existing successful identity and six-language navigation.

## 7. IDBA CORE boundary
Shared core: entry state, graph contract, route selection, rendering interfaces, context/enquiry identifiers, analytics contract, CRM adapter contract, cultural presentation contract and build checks.
Project adapters: ontology, translations, brand/design tokens, cases, offers, permissions, contact configuration and local workflows.
Extract only working, tested abstractions from YISHU; avoid premature generic platform or migration of other products. Reuse versioned core; each product retains its own ontology and boundaries. No public claims that IDBA is a finished separate product yet.

## 8. Migration sequence
M0: snapshot main; inventory URLs, six-language coverage, existing cases, assets, domain and build/deploy process.
M1: standard and backwards-compatible intake identifiers; keep current pages and mail handoff.
M2: port graph schema, source ledger mapping, navigator and route generation from Claude archive; merge into existing UX and all locale contracts; compare legacy and new routes.
M3: full portfolio reconciliation and cultural engine. Preserve original source ledger and mark unknowns.
M4: actual submission endpoint, CRM adapter, aggregate analytics, privacy review and payment gateway integration. No real data in test fixtures.
M5: PES visual and functional QA, browser and mobile test, SEO/canonical/hreflang, links, performance, accessibility, submission delivery/CRM verification and China connectivity where relevant.
M6: review and release without losing existing functionality; test rollback; verify live domain. Then extract reusable IDBA core for other RFS products.
Release gate: no regression in six language navigation, CNAME, case pages, URLs and corporate contacts; no unapproved public prices or personal data in analytics; actual browser tests and verified enquiry delivery before claiming completion. Static checks alone are insufficient.
