# PRODUCT EXPERIENCE STANDARD — PES v1.0
**Scope:** YISHU.BUSINESS — all public pages, localized routes, demos and case presentations.
**Date:** 2026-11-27. Additive implementation standard; not a replacement for approved product, content, case, semantic or data architecture.

## 1. Non-negotiable principles
1. ATTRACTION — create visible value before asking for attention, data, money or a meeting. The first viewport must present a distinctive product identity and a meaningful visual proposition, not a wall of explanation.
2. VRL — communicate in the visitor's language of recognition, situations, goals and transitions; keep internal ontology and implementation jargon behind the interface.
3. ARCHITECTURAL REVEAL — make a hidden opportunity visible through concrete, context-specific demonstrations. Aim for the reaction “Что, так можно было?” / “That was possible?” without inventing results.
4. RBDA (Role-Based Depth Architecture) — one product, multiple levels of depth. Make executive, operational and engineering perspectives available where relevant; never force every visitor through all details.
5. CEA (Continuous Experience Architecture) — information expands where interest arises. Default to a continuous reading flow, inline disclosure and local controls. Do not make visitors jump between distant anchors to understand one idea. Keep global navigation accessible in a compact menu; retain direct URLs for intentional entry and sharing.
6. LIVE DEMONSTRATION — prefer working interactive models, before/after comparisons, diagrams, meaningful visualizations and immediate feedback over descriptive claims. Label illustrative scenarios and distinguish them from observed outcomes.
7. COLLABORATION — offer a relevant next step immediately after the visitor experiences enough value; repeat a concise contact route at the end. Do not bury the only CTA after technical detail.
8. VISUAL FIDELITY — preserve the strongest approved visual elements when implementing the page. The final rendered site must meet or exceed the reference demonstration in visual clarity and impact.

## 2. Product page choreography
Identity → recognition → visual reveal → interaction → experienced value → relevant next step → optional depth → contact.
The sequence is a design default, not a rigid template. Choose the most natural route for each visitor and intent. Keep one coherent product with multiple views of the same underlying content and data.

## 3. YISHU.BUSINESS application
- Preserve the approved master prompt, case presentation standard, source ledger, knowledge graph and context model. Do not replace these with this standard.
- Main proposition: «Мы не вписываем ваше будущее в архитектуру прошлого».
- Lead with business transitions and recognizable situations rather than lists of disciplines. Use the Business Navigator as a meaningful product interaction, not a forced questionnaire. Keep conventional navigation available.
- Clearly distinguish current, desired and potential states. Potential Discovery is a distinct service, not a guaranteed answer supplied by a superficial quiz.
- Keep geographic direction (Inbound / Domestic / Outbound / Regional) independent of transition type (Development / Transformation / Integration / Protection).
- Show role-appropriate paths for founders, executives, practitioners and implementation partners where applicable. Preserve localized routes and native-language quality (RU, KY, KK, UZ, ZH, EN).
- Every case must preserve its approved narrative: reality → hidden opportunity → architectural reveal → system → language → visual demonstration → value → scaling. Use the entire approved portfolio, not a handful of examples. Distinguish concepts, prototypes, actual implementations and observed outcomes.
- Preserve the commercial progression from Navigator through Potential Discovery, Architecture Design, Implementation and Continuous Development. Provide context-appropriate actions, transparent scope and direct contact.

## 4. Visual and interaction implementation
- Build a visual storyboard and responsive prototype before completing the page. Establish typography, signature visual motifs, spacing, color semantics and movement as one design system.
- Each visual must perform a job: recognition, comparison, explanation, demonstration or decision support. No meaningless decoration, stock imagery merely to fill space, or excessive animated effects.
- Use actual interactive controls with immediate, consistent state updates; offer reset, sensible defaults and legible labels. Never present a decorative control as working.
- Prefer inline expandable details for technical depth; keep the primary flow concise. Avoid repeated copy, internal jargon, large unstructured text blocks and redundant links.
- Mobile first: no unintended horizontal overflow; for deliberately wide content, display a persistent affordance, usable controls or native scrollbar, and indicate direction/progress when helpful. Touch targets and type must remain usable.
- Motion should explain changes or support orientation, not slow navigation. Respect prefers-reduced-motion, keyboard access, visible focus and semantic labels. Avoid hiding necessary information until animation completes.
- Keep first load light and fast; use appropriate SVG, optimized assets and progressive enhancement. Provide useful fallbacks.
- Public content must not expose private information, unpublished material or unsupported claims. All illustrative data, simulations and hypothetical outcomes must be clear.
- Follow the established corporate contact standard and keep contact forms honest about submission status.

## 5. Acceptance gates (required before calling a page finished)
A. Content and architecture: all approved requirements retained; role routes and language appropriate; no invented results or broken references.
B. Visual: inspect rendered screenshots at mobile (360–390 px), tablet (768 px) and desktop (1440 px); compare with approved concept; first viewport conveys value without scrolling on ordinary layouts where practicable.
C. Interaction: run every important control, disclosure, navigation, form and reset; verify keyboard and touch behavior, state synchronization, empty and failure states.
D. Reading flow: test sequential scrolling; explanations local to visuals; no mandatory anchor hopping; visible horizontal scroll affordances where necessary.
E. Accessibility and performance: check contrast, focus, reduced motion, overflow, layout shifts, asset weight and error console. Target Core Web Vitals good thresholds when measurable, without claiming unmeasured scores.
F. Commercial: relevant CTA appears after value demonstration; contact details correct; no dead ends; no forced intake before basic value is understood.
G. Deployment: verify the actual public URL after deployment; distinguish committed code from successful public rendering. Record commit, verified viewports and any remaining blockers.
A page with unverified visual or functional quality is not a completed release.

## 6. Working protocol
1. Preserve source architecture and select a visitor intent.
2. Design first viewport and visual narrative; prototype the actual interactions.
3. Build responsive product experience and optional depth.
4. Run acceptance gates, fix issues, then deploy and verify.
5. Treat improvements discovered during implementation as reusable design patterns; propose architectural changes separately rather than silently replacing approved decisions.

This standard specifies product experience and quality gates. It does not authorize changing established strategy, pricing, claims, legal terms or data handling without agreement.
